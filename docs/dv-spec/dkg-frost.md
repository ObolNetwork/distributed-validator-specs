# FROST DKG Interoperability Spec

This document describes the FROST distributed key generation (DKG) protocol used to generate BLS validator keys for a distributed validator cluster.

FROST is the **default** algorithm: a cluster definition whose `dkg_algorithm` field is `default`, `frost`, or empty runs FROST. [Pedersen DKG](dkg-pedersen.md) is the opt-in alternative, selected with `dkg_algorithm: pedersen`.

Scope:

- Over-the-wire message shapes and fields
- Message IDs, the libp2p protocol ID, and how each round is transported
- Receiver-side validation rules and round completion conditions
- The DKG context string that binds a ceremony to its cluster
- Output artifacts

Out of scope: FROST cryptography (Feldman verification, secret sharing, key derivation), reliable broadcast mechanics, ceremony step synchronisation.

**Note**: This document describes the cryptographic DKG protocol only. See [DKG Sync Protocol](dkg-sync.md) for ceremony management and [Reliable Broadcast](reliable-broadcast.md) for the broadcast component the cast rounds rely on.

## Terms and Notation

- `n`: number of participating nodes in the ceremony
- `t`: cluster signing threshold (default ceil(2n/3))
- `numVals`: number of distributed validators generated by *this* ceremony — for an append-validators run this is the number of **new** validators, not the cluster total
- `ValIdx`: 0-based index of a distributed validator within this ceremony
- `ShareIdx`: 1-based participant ID, equal to `PeerIdx + 1`
- `Suite`: BLS12-381; public points on G1 (48-byte compressed), scalars 32 bytes

## Protocol Identifiers

FROST derives all of its IDs from a common prefix:

```
/charon/dkg/frost/2.0.0
```

| ID                                       | Kind                | Transport                                              |
| ---------------------------------------- | ------------------- | ------------------------------------------------------ |
| `/charon/dkg/frost/2.0.0/round1/cast`    | bcast message ID    | Reliable broadcast over `/charon/dkg/bcast/1.0.0/{sig,msg}` |
| `/charon/dkg/frost/2.0.0/round1/p2p`     | libp2p protocol ID  | Direct length-delimited protobuf stream to one peer     |
| `/charon/dkg/frost/2.0.0/round2/cast`    | bcast message ID    | Reliable broadcast over `/charon/dkg/bcast/1.0.0/{sig,msg}` |

Two distinctions matter for interop:

- The two `cast` IDs are **not** libp2p protocol IDs. They appear as the `id` field of `BCastSigRequest` and `BCastMessage`, and the bytes travel over the reliable broadcast protocol IDs. Only `round1/p2p` has its own libp2p stream handler.
- Charon builds these strings by path-joining a suffix onto the literal `"/charon/dkg/frost/2.0.0/"`. The join normalises the path, so the trailing slash of that source literal **does not** appear on the wire. Implementations must use the exact strings in the table above.

The commitments and proofs of round 1, and the public keys of round 2, are broadcast because every node must see the identical set; the Shamir shares of round 1 are sent directly because each is secret to one recipient.

## DKG Context String

Every participant feeds a context string into FROST key generation, binding the ceremony to its cluster. It is the cluster definition hash formatted as lowercase hex with a `0x` prefix (Go's `%#x` verb):

```
ctx = "0x" + hex(definition_hash)
```

A mismatched context makes the ceremony fail rather than silently produce diverging keys. See [`frost_dkg_context`](../../src/dv_spec/subspecs/dkg/frost.py).

## Message Schemas

The following protobuf definitions are used over the wire:

- [frost.proto](../../proto/frost.proto) — FROST round 1 and round 2 message definitions
- [nodesigs.proto](../../proto/nodesigs.proto) — node signature exchange

See the Python reference implementation: [`dv_spec.subspecs.dkg.frost`](../../src/dv_spec/subspecs/dkg/frost.py) and [`dv_spec.subspecs.dkg.node_sigs`](../../src/dv_spec/subspecs/dkg/node_sigs.py).

Every payload carries a `FrostMsgKey`:

| Field       | Meaning                                                                |
| ----------- | ---------------------------------------------------------------------- |
| `val_idx`   | Distributed validator index within this ceremony, 0-based              |
| `source_id` | Sender's `ShareIdx`, 1-based                                           |
| `target_id` | Recipient's `ShareIdx`, 1-based; `0` marks a broadcast                 |

All validators share the two transport rounds, so a single bundle carries one entry per validator and the key tells the receiver which parallel FROST instance each entry belongs to.

## Ceremony Sequencing

FROST runs `numVals` instances in parallel, synchronised at the two transport rounds. A node completes each local round for every validator before transporting anything, so there are exactly two broadcast rounds regardless of validator count.

### Round 1

1. For each validator index `0..numVals-1`, run local FROST round 1, producing a broadcast (`wi`, `ci`, `commitments`) and one Shamir share per other participant.
2. Bundle all validators' broadcasts into one `FrostRound1Casts` and reliably broadcast it under `round1/cast`. Feed a copy to self — the local node's own bundle is part of its expected input set and does not pass through the receive validation path.
3. Group the Shamir shares by recipient, and send one `FrostRound1P2P` per peer over `round1/p2p`. No message is sent to self.
4. Wait for `n` cast bundles (including own) and `n - 1` direct bundles.

### Round 2

1. For each validator, run local FROST round 2 over the round 1 casts and shares received for that validator index, producing the aggregate `verification_key` and this node's `vk_share`.
2. Bundle all validators' casts into one `FrostRound2Casts` and reliably broadcast it under `round2/cast`. Feed a copy to self.
3. Wait for `n` cast bundles (including own).

### Node Signature Exchange

After the DKG rounds, the ceremony signs, exchanges and aggregates deposit data, validator registrations and the cluster lock hash (see [DKG Sync Protocol](dkg-sync.md) for the step sequence). The final wire-visible step is the node signature exchange, which is algorithm-independent and shared with Pedersen and the operator-edit protocols:

- Message ID `/charon/dkg/node_sig` — note there is no version component, unlike every other DKG ID.
- Each node broadcasts `MsgNodeSig{signature, peer_index}` where `signature` is a 65-byte secp256k1 `R || S || V` signature over the cluster lock hash, produced with the node's ENR private key, and `peer_index` is its own 0-based peer index.
- Receivers check that `peer_index` is in range, is not the receiver's own index, and matches the peer index resolved from the libp2p sender identity — a peer cannot deposit a signature into another peer's slot. The signature is then verified against that peer's ENR public key over the lock hash.
- Collection completes only when **all** `n` slots are filled. There is no threshold here: the lock file carries one signature per operator.
- Protocols where a participant has nothing to sign (for example an operator being removed) broadcast the 4-byte sentinel `0xdeadbeef` in place of a signature. Sentinel entries are not verified and are dropped from the collected set, so the resulting list can be shorter than `n`. A node that itself holds no key treats every received signature as a sentinel.

## Validation Rules

A conforming receiver MUST enforce the following before accepting a bundle. Each rule applies to *every* entry in the bundle, so one bad entry rejects the whole bundle.

**Round 1 casts** (`FrostRound1Casts`):

- `key.source_id` equals the `ShareIdx` of the broadcasting peer
- `key.target_id` equals `0`
- `key.val_idx` is in `[0, numVals)`
- `len(commitments)` equals exactly `t`

**Round 1 direct** (`FrostRound1P2P`):

- `key.source_id` equals the `ShareIdx` of the sending peer
- `key.target_id` equals the receiver's own `ShareIdx`
- `key.val_idx` is in `[0, numVals)`

**Round 2 casts** (`FrostRound2Casts`):

- `key.source_id` equals the `ShareIdx` of the broadcasting peer
- `key.target_id` equals `0`
- `key.val_idx` is in `[0, numVals)`

**Deduplication and flood limits:**

- At most one bundle per peer per message ID is accepted; later bundles from the same peer under the same ID are ignored, not treated as errors.
- Receiving more than `n` round 1 cast bundles, more than `n - 1` round 1 direct bundles, or more than `n` round 2 cast bundles is an error that fails the ceremony.

**Not validated by Charon** (documented so implementations do not assume otherwise):

- The number of entries in a bundle is not checked against `numVals`, and a `val_idx` may repeat within a bundle. A bundle missing a validator's entry stalls the corresponding FROST instance rather than being rejected outright.
- `wi`, `ci`, `commitments`, `vk_share` and `verification_key` lengths are not checked at the message layer; malformed points and scalars are rejected when decoded.
- Peers' `verification_key` values are **not** cross-checked against each other or against the locally derived key. A divergent peer is only detected later, when the cluster lock signatures are verified.

## Output Artifacts

Per validator index, in ascending order, a successful ceremony yields:

- `validator_pubkey`: the aggregate validator public key (48-byte compressed G1), taken from the **local** FROST instance
- `secret_share`: this node's private share (32-byte scalar), taken from the local FROST instance
- `public_shares`: map from 1-based `ShareIdx` to that node's `vk_share`, collected from the round 2 casts including this node's own

This is the same artifact a Pedersen ceremony produces; see [`dv_spec.subspecs.dkg.share`](../../src/dv_spec/subspecs/dkg/share.py) and [`assemble_validator_shares`](../../src/dv_spec/subspecs/dkg/frost.py).

## Interop Notes

- **Self-echo is load-bearing**: a node must count its own cast bundle toward the `n` it waits for, or round 1 and round 2 never complete.
- **`n` versus `n - 1`**: round 1 expects `n` cast bundles but only `n - 1` direct bundles. Off-by-one here manifests as a ceremony that hangs to timeout.
- **`numVals` is per-ceremony**: when appending validators to an existing cluster, indices restart at 0 for the new validators only.
- **`ShareIdx` is 1-based** in FROST keys, while `peer_index` in `MsgNodeSig` is 0-based. Both appear in the same ceremony.
